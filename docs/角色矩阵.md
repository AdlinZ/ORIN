# ORIN 角色矩阵

本文档定义当前首版权限口径。现阶段先收敛为两类角色：管理员与普通用户；后续再把具体资源权限拆成可赋予用户的细粒度能力。

## 1. 角色定义

| 角色 | 定位 | 默认入口 | 可见模块 |
|------|------|----------|----------|
| `ROLE_ADMIN` | 管理员 | `/admin/admin-overview` | ORIN 管理台 + ORIN 工作台；通过产品切换器显式切换 |
| `ROLE_USER` | 普通用户 / 创作者 | `/chat` | ORIN Chat + 本人资源范围的 ORIN 工作台；不可进入管理台 |

开发者 / API 调用方使用 `/platform` 作为主入口，当前提供个人 `CLIENT_ACCESS` Key 创建、轮换、禁用、MCP 配置与调用历史。现阶段开发者仍复用 `ROLE_USER` 权限边界，后续再拆更细粒度的 API 调用方能力。

个人账号可通过 `/register` 自助创建，前提是后端 `ORIN_AUTH_SELF_REGISTRATION_ENABLED=true`。自助注册只授予 `ROLE_USER`，不会创建管理员、部门或组织权限。

兼容口径：前端仍识别历史 `ADMIN` / `USER` 字符串；后端权限判断以 `ROLE_*` 为准。所有角色 token 必须携带 `roles` claim（参见 `AGENTS.md` §5.3）。

## 2. 前端权限口径

- 菜单来源统一为 `orin-frontend/src/router/topMenuConfig.js`。
- 管理员默认进入 `/admin`，管理台只展示平台控制与运行观测；应用构建和资源知识通过产品切换器进入 `/workspace`，不再混排在同一导航。
- 普通用户默认进入 `/chat`，可通过头像菜单或产品切换器进入 `/workspace`；只能访问本人可见的智能体、工作流、知识库、协作、Skill、MCP、会话与 Trace，访问 `/admin/*` 会被路由守卫拦截。
- `/platform` 面向开发者 / API 调用方开放，但只允许用户管理自己拥有的 `CLIENT_ACCESS` Key。
- `/register` 是公开入口，只用于创建个人 `ROLE_USER` 账号；已登录用户访问时仍按已有 token 进入角色默认页。
- `/dashboard` 根路径按角色默认入口跳转；用户显式访问有权限的具体页面时不再被默认首页覆盖。
- `/chat` 路由显式声明 `meta.roles: USER_MENU_ROLES`，未来如果出现无 `ROLE_USER` claim 的管理员能稳定被挡。

### 2.1 导航布局（双 nav + 用户切换）

前端保留 **sidebar / topbar 两种 nav 布局并存**，不收敛为单一形态：

- `menuMode` 持久化在 `localStorage`（`orin_menu_mode`），用户可在 `Sidebar` 底部或 `TopNavbar` 操作区的「菜单模式」按钮一键切换，刷新后保留选择
- 管理员登录后默认进入 sidebar（历史主形态），普通用户默认进入 sidebar（新装用户），但都不会在登录时强覆盖已存在的偏好
- 两种布局共享 `MainLayout`、路由树、菜单配置与权限策略；切换不会改变可见菜单，只改变渲染形态
- 用户头像菜单的 `ORIN 工作台` 入口与 `getDashboardGuardRedirect` 路由守卫在两种布局下行为一致

后续如需按角色/产品面锁死单一布局（例如 chat 面强制 topbar），再讨论；当前选择是「用户自决 + 跨形态体验一致」。

> 决策记录：见 `路线图.md` Phase 1.5；本设计由 2026-07 Phase 6 决策拍板（选项 C：保持双 nav + 用户可切换）。

### 2.2 URL canonical（Phase 7b 全闭合）

URL 以 **chat / workspace / admin** 三套路径为 canonical：

- canonical 入口：`/chat/*`、`/workspace/*`、`/workspace/knowledge`、`/admin/*`、`/admin/runtime/*`；旧路径 `/dashboard/applications/*`、`/dashboard/control/*`、`/dashboard/runtime/*`、`/dashboard/resources/*` 由 `LEGACY_ROUTE_REDIRECTS` 兜底 redirect 到 canonical
- 4 个 parent mount（`applications`、`control`、`runtime`、`resources`）已从 `/dashboard.children` 迁到 top-level 独立路由（`/workspace`、`/admin`、`/admin/runtime`、`/workspace/knowledge`）；`/dashboard.children` 仅保留 redirect entries + 个人中心（`profile` + `mcp`）
- `routes.js` 的 `ROUTES.*` 常量与 `LEGACY_ROUTE_REDIRECTS_RAW` 双轨切换：常量指向新路径（`agentRoutes.LIST = /workspace/agents`），redirect keys 仍保留旧路径形式以便命中跨版本链接
- 路由守卫 `getDashboardGuardRedirect` 同步识别新路径为有效 surface
- `getDefaultHomeByRoles(['ROLE_ADMIN'])` 返回 `ROUTES.ADMIN`（`/admin/admin-overview`）替代 `/dashboard/control/admin-overview`

本轮完成 Phase 7b 后，访问任一旧 `/dashboard/*` 子路径都会经 LEGACY redirect 跳到 `/workspace/*` 或 `/admin/*`，URL bar 同步更新为 canonical。

## 3. 后端权限口径

- 当前前端只暴露 `ROLE_ADMIN` 与 `ROLE_USER` 两类角色。
- `/api/v1/users/**`、`/api/v1/departments/**`、`/api/v1/roles/**` 属于管理员能力。
- `/api/v1/api-keys/**` 分为两类：`ROLE_ADMIN` 可做全局治理；`ROLE_USER` 只能管理自己拥有的 `CLIENT_ACCESS` Key。
- 普通用户 API Key 所有权只来自 JWT 当前用户，不能通过 `X-User-Id` 或 `targetUserId` 覆盖；访问他人 Key 按不可见处理。
- API Key 明文回显、配额重置与 `PROVIDER_CREDENTIAL` 仍仅限管理员；`MCP_ENV` 支持普通用户管理本人密钥，跨用户引用由 owner ACL 拒绝。
- `/api/v1/model-config/**`、`/api/v1/tasks/**` 全局任务队列和 `/api/v1/knowledge/diagnose/**` 基础设施诊断仅限管理员。
- `/api/v1/conversation-logs/**` 对管理员保留全局视图，普通用户按 JWT userId 与会话 owner 过滤。
- `/v1/**` API Key 通道与 `/api/v1/**` JWT 业务通道继续隔离。
- `/api/v1/auth/register` 是公开认证入口，成功后 JWT 必须携带 `roles=["ROLE_USER"]`。

### 3.1 ROLE_USER 后端可访问端点

普通用户通过 `/chat` 触达的后端接口，列表如下（不视为新加接口，全部归入既有前缀）：

| 路径前缀 | 用途 |
| --- | --- |
| `GET /api/v1/agents` | 列出当前用户可用的智能体 |
| `GET /api/v1/agents/chat/sessions` | 列出会话；`?agentId=` 过滤 |
| `POST /api/v1/agents/chat/sessions` | 创建会话 |
| `DELETE /api/v1/agents/chat/sessions/{id}` | 删除会话 |
| `GET /api/v1/agents/chat/sessions/{id}` | 会话元信息 |
| `GET /api/v1/agents/chat/sessions/{id}/messages` | 会话消息（`?limit=&before=` 翻页） |
| `POST /api/v1/agents/chat/sessions/{id}/messages` | 发送消息（blocking） |
| `POST /api/v1/agents/chat/sessions/{id}/messages/stream` | 发送消息（SSE 流式） |
| `GET /api/v1/agents/chat/sessions/{id}/kbs` | 列出已附加知识库 |
| `POST /api/v1/agents/chat/sessions/{id}/attach-kb` | 附加知识库 |
| `POST /api/v1/agents/chat/sessions/{id}/detach-kb` | 解绑知识库 |
| `GET /api/v1/knowledge/list` | 知识库选择器（仅返回用户有权访问的子集） |
| `POST /api/v1/multimodal/upload` | 附件上传（仅本人可见文件 id） |
| `GET /api/v1/api-keys/**` | 仅本人 `CLIENT_ACCESS` Key 的 CRUD / 轮换 / 历史 |

会话为 owner 范围：`owner_user_id` 来自 JWT 主体（`POST /sessions` 创建时服务端写入），跨用户访问按 404/403 处理；历史 NULL-owner 会话仅管理员/运维可见。

`/api/v1/users/**` 等管理员接口继续对 ROLE_USER 返回 401/403。

### 3.2 /chat Token 过期提醒

`TokenExpiryWarning` 组件在 `/chat` 与 `/dashboard/*` 都启用，剩余时间 < 5 分钟会展示「登录即将过期」提醒并提供「立即重新登录」入口。SSE / blocking 通道在请求层都会触发 `request.js → buildErrorMessage`，错误响应统一带 `traceId` 并暴露在对话区。

## 4. 后续边界

- 细粒度权限后续按“权限赋予用户”的方式做，不再先扩展一批固定角色。
- 后续权限拆分优先围绕资源访问、API Key 能力、模型 / 知识库 / 工作流管理边界展开。
